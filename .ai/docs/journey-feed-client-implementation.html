Journey Feed · Implementação Client-Side

📅 Junho 2026 🏷️ apps/client/src/features/feed/journey/ 📄 PR #25

1. Visão Geral

O Journey Feed é a experiência principal de leitura bíblica do Versum. O usuário percorre a Bíblia sequencialmente (Gênesis ao Apocalipse) em um feed vertical com snap scrolling estilo TikTok. Cada capítulo ocupa uma tela inteira e é dividido em páginas horizontais de versículos.

Diferente de apps de leitura tradicionais (rolagem infinita ou paginação simples), o Journey Feed foi projetado para ser imersivo e navegável por gestos: scroll vertical troca de capítulo, scroll horizontal navega entre páginas de versículos.

2. Stack

⚛️

React 19 + Next.js 16

App Router, Server Components com ilhas de interatividade client-side.

📡

TanStack Query v5

useInfiniteQuery para feed infinito, useMutation para progresso.

🎯

Snap vertical entre capítulos e horizontal entre páginas — zero JS de scroll.

📐

DOM Measurement

Medição de altura real de cada versículo no DOM para paginação adaptativa.

4. Fluxos de Dados

4.1 Carregamento Inicial

JourneyFeed monta ↓ useJourneyFeed() → useInfiniteQuery(queryKey: ['journey-feed']) ↓ fetchFeed({ "buffer-size": 4 }) → GET /api/v1/readings/journey/feed ↓ API retorna { data: { current, nextItems, progress } } ↓ extractChapters() extrai current + nextItems → dedup via Set<chapterId> → armazena em chaptersRef ↓ chapter-view.tsx: 1. Renderiza probe oculto com TODOS os versículos 2. Mede offsetHeight individual de cada um (+ margin-bottom) 3. Empacotamento guloso: enche páginas até o limite do container 4. setPages(resultado) ↓ Renderiza VersesPage para cada página calculada

4.2 Scroll Vertical (entre capítulos)

Usuário scrola verticalmente ↓ CSS scroll-snap-type: y mandatory + scroll-snap-align: start → navegação nativa instantânea (sem JS) ↓ useActiveChapter (IntersectionObserver, threshold: 0.5) → detecta qual capítulo está em view ↓ Se capítulo saiu de view: → setTimeout 500ms (debounce) → POST /api/v1/readings/journey/next (marca como lido) ↓ Se activeIndex >= chapters.length - 2: → fetchNextPage() → POST /next + GET /feed → novos capítulos dedupados

4.3 Scroll Horizontal (dentro do capítulo)

Usuário scrola horizontalmente ↓ useChapterPagination: → addEventListener('scroll') + requestAnimationFrame → activePage = Math.round(scrollLeft / clientWidth) ↓ ChapterHeader re-renderiza: → "Gênesis 1 • 1-7 ●○○○○" → "Gênesis 1 • 8-14 ○●○○○" ↓ Dots atualizados via activePage

4.4 Navegação por Teclado

useKeyboardNavigation: → document.addEventListener('keydown') ↓ ArrowDown: → encontra índice do capítulo visível (centro do container) → scrolla para o próximo [data-chapter-id] ↓ ArrowUp: → scrolla para o capítulo anterior ↓ ArrowLeft/ArrowRight: → nativo (scroll-snap-type: x mandatory no container horizontal) ↓ prefers-reduced-motion: → scroll-behavior: 'auto' em vez de 'smooth'

5. Algoritmo de Paginação Adaptativa core

Este é o coração da implementação. Diferente de abordagens estáticas (「X versículos por página」) ou amostragem (medir 5 e estimar), nós renderizamos todos os versículos em um probe oculto e medimos a altura real de cada um no DOM.

Por que abordagens anteriores falhavam

Abordagem Problema
Versículos fixos por página Ignora variação de tamanho. Um versículo de 3 palavras e um de 300 palavras ocupam o mesmo slot → overflow ou desperdício.
Amostragem (primeiros 5) Se os primeiros 5 são curtos, a média é baixa, calculamos versículos demais, e os versículos longos no meio do capítulo estouram o layout.
Altura total / container Diz quantas páginas, mas não distribui corretamente — versículos longos e curtos não se encaixam em divisão igual.

Algoritmo atual (greedy packing com medição individual)

1. Renderiza TODOS os versículos em um <div> oculto (position: absolute,
   visibility: hidden, paddingLeft/Right igual ao VersesPage)

2. Para cada <p data-verse-id>, mede:
     totalHeight = element.offsetHeight + 16  // offsetHeight + margin-bottom (mb-4)

3. Calcula altura disponível por página:
     availableHeight = container.clientHeight - 40  // 2.5rem de padding vertical

4. Empacotamento guloso:
     para cada versículo:
       se (usedHeight + totalHeight > availableHeight) E página não está vazia:
         finaliza página atual, inicia nova
       adiciona versículo à página atual
       usedHeight += totalHeight

Propriedades do algoritmo

📏 Precisão real

Cada versículo é medido no DOM real com o texto completo, fonte, line-height e wrapping de linha exatos.

🔄 Adaptativo a fontes

Funciona com qualquer tamanho de fonte, zoom do navegador, ou mudança de dispositivo — a medição é sempre no contexto renderizado.

🛡️ Sem overflow

O greedy packing respeita o limite de altura. Se um versículo for muito longo, ele ganha sua própria página.

📐 Recalcula no resize

ResizeObserver no container dispara nova medição quando a janela muda.

6. Arquitetura de Decisões

6.1 Por que medir todos os versículos no DOM em vez de estimar?

Problema: Versículos bíblicos têm comprimento extremamente variável. João 11:35 ("Jesus chorou.") tem 2 palavras. Salmo 119 tem versículos de 30+ palavras. Qualquer fórmula baseada em caracteres ou média amostral produz erro sistemático.

Decisão: Renderizar todos os versículos em um probe position: absolute; visibility: hidden com o mesmo padding lateral do VersesPage. Medir offsetHeight individual. Empacotamento guloso.

Custo: ~2x DOM nodes (probe + páginas visíveis). Para Salmo 119 (176 versículos), são ~350 nodes — irrelevante para navegadores modernos. O ganho em precisão supera amplamente o custo.

6.2 Por que CSS Scroll Snap em vez de JS?

Snap scrolling com JS (calculando posições manualmente) é frágil, propenso a race conditions e consome CPU no main thread. CSS scroll-snap-type é nativo, roda no compositor thread, e funciona em touch, trackpad e mouse sem código.

6.3 Por que IntersectionObserver em vez de onScroll?

onScroll com scroll-snap-type: y mandatory dispara centenas de eventos por segundo. IntersectionObserver é passivo e só notifica quando o estado de interseção muda — perfeito para detectar "capítulo X entrou/saiu de view".

6.4 Por que inline styles para snap/pagination CSS?

O projeto usa Tailwind CSS v4, que compila @utility classes em tempo de build. Classes utilitárias para scroll-snap se comportavam inconsistentemente entre builds. Inline styles garantem que as propriedades sempre estejam presentes, independente do estágio de compilação.

6.5 Por que direct fetch() em vez de Orval nos hooks core?

O use-journey-feed.ts usa fetch() direto com a URL gerada pelo Orval (getGetApiV1ReadingsJourneyFeedUrl), mas não usa o hook gerado. Isso porque o useInfiniteQuery precisa de controle fino sobre queryFn, getNextPageParam e maxPages — o código gerado pelo Orval não expõe esses parâmetros adequadamente para infinite queries.

6.6 Por que ref pattern em vez de useCallback para estabilidade de effects?

Problema: Sem useCallback/useMemo manual (React Compiler), funções como markPreviousAsRead ou update são recriadas a cada render. Se usadas como dependência de useEffect, causariam re-subscriptions contínuas.

Decisão: Armazenar values mutáveis em refs (isAtEndRef, chaptersRef, fetchNextPageRef, updateRef) e lê-los como .current dentro do effect. O useEffect depende apenas de [containerRef], nunca recria observers/listeners, e sempre lê o valor mais recente via ref.

6.7 Por que remover useCallback/useMemo manual?

O projeto usa React Compiler (babel-plugin-react-compiler 1.0.0), que auto-memoiza funções, valores e componentes durante a compilação. useCallback e useMemo explícitos tornam-se ruído — o compilador gera o mesmo código ou melhor. A remoção seguiu o princípio: "se o compilador faz, não escreva."

7. Tratamento de Erros

🌐 Erro de rede

retry: 2 (3 tentativas). Se persistir, exibe mensagem + botão "Tentar novamente" que chama refetch().

❌ Erro no POST/next

Apenas log no console (operação em background). Próximo scroll tenta novamente.

⏱️ Timeout

AbortSignal herdado do TanStack Query. Fetch cancelado automaticamente.

🔒 401 (sessão expirada)

Middleware de autenticação no proxy redireciona para /login antes do feed carregar.

9. Performance

  • maxPages: 3 no useInfiniteQuery — só mantém 3 snapshots na memória
  • React Compiler — auto-memoiza funções e valores; sem useCallback/useMemo manual
  • Ref pattern — isAtEndRef, chaptersRef, fetchNextPageRef, updateRef evitam re-subscriptions de effects
  • maxPages: 3 no useInfiniteQuery — só mantém 3 snapshots na memória
  • useRef para seenChapterIds — evita re-render em dedup
  • requestAnimationFrame no scroll horizontal — throttling natural
  • scroll-behavior: smooth nativo — sem animação JS
  • staleTime: 60s — evita refetch desnecessário
  • Probe oculto — renderizado mas não visível; visibility: hidden preserva layout sem pintar
